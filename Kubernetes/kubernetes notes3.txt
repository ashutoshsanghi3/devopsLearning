Correct Flow When a Node Goes Down in Kubernetes:-
✅ API Server updates etcd when a node is unresponsive.
✅ Node Controller marks the node as unhealthy and evicts pods after a timeout.
❌ Node Controller does NOT replace pods—it only removes them from the API Server.
✅ Replication Controller (or Deployment, StatefulSet, etc.) schedules new pods on available nodes.
❌ Pods are not rescheduled immediately—eviction happens after a default 5-minute delay (configurable).

How Deployment Creates and Manages a ReplicaSet (Step-by-Step):-
1. User creates a Deployment → Kubernetes stores it in etcd.
2. Deployment Controller detects the new Deployment → Creates a ReplicaSet.
3. ReplicaSet ensures the required number of Pods → Creates and manages Pods.
4. Kubernetes Scheduler assigns Pods to available nodes → Pods start running.
5. Deployment continuously monitors the ReplicaSet → Ensures desired Pods are running.
6. If a Pod fails, the ReplicaSet automatically replaces it → Maintains availability.
7. When updating a Deployment (e.g., new image):

A new ReplicaSet is created for the update.
The old ReplicaSet is gradually scaled down while new Pods are created.
8. Old ReplicaSet is retained (scaled to zero) → Enables easy rollback.

✅ Deployment → ReplicaSet → Pods (Deployment controls rollout, ReplicaSet manages Pods).
✅ Automatic healing, updates, and rollbacks handled efficiently.

What Happens When a Deployment is Updated?
When you update a Deployment (e.g., change the container image), Kubernetes does NOT modify the existing ReplicaSet. 
Instead:
-A New ReplicaSet is Created for the updated Deployment.
-Pods from the Old ReplicaSet are Gradually Scaled Down, while new Pods are created from the new ReplicaSet.
-Once the update is complete, the old ReplicaSet remains but is scaled to zero replicas (for rollback purposes).
