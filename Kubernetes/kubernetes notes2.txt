Creation of Pod in Kubernetes ->

1. User Requests Pod Creation

A user submits a request to create a pod using kubectl, which sends an API request to the Kubernetes API Server. The request includes authentication credentials and necessary configurations.

2. API Server Processes the Request

The API Server authenticates the request, verifies user permissions via RBAC, validates the pod specification, and then stores the pod definition in etcd, the cluster’s key-value store.

3. Scheduler Assigns the Pod to a Node

The Scheduler selects the best node for the pod based on resource availability, constraints, and affinity rules. It then updates etcd with the scheduling decision.

4. API Server Notifies the Kubelet

The API Server informs the Kubelet (running on the assigned node) about the new pod and its desired state. The Kubelet then prepares to run the pod.

5. Kubelet Interacts with the Container Runtime (CRI)

The Kubelet communicates with the Container Runtime (e.g., containerd, Docker, or CRI-O) to:

	Pull the container image (if not already available).

	Create and start the container.

	Configure networking using CNI (Container Network Interface).

6. Pod Becomes Running

Once the container is successfully created, it joins the pod’s network, gets an IP address, and starts executing its application.

7. Monitoring and Pod Self-Healing

If a container inside the pod crashes, the Kubelet restarts it based on the restart policy.

If the entire node fails, the Node Controller detects the failure and reschedules the pod on another node.

8. Controllers Maintain Desired State

The Controller Manager ensures the pod count and health match the defined specification. ReplicaSets, Deployments, and other controllers monitor and restore pods if they crash or are deleted.

Types of controller(Check through gpt)->

Node Controller → Monitors node health; if a node fails, it evicts pods and reschedules them.
ReplicaSet Controller → Ensures the specified number of pod replicas are running.
Deployment Controller → Manages rolling updates and rollbacks using ReplicaSets.
Job Controller → Runs one-time jobs until completion, retrying if needed.
DaemonSet Controller → Ensures one pod runs on every node (e.g., for monitoring/logging).
StatefulSet Controller → Manages pods with persistent identities and storage.
CronJob Controller → Schedules jobs to run at specific times.
Token Controller → Manages service account tokens for API authentication.

gRPC in kube-apiserver Communication ->
gRPC (Google Remote Procedure Call) is a high-performance, open-source RPC framework used by internal Kubernetes components (such as the scheduler, controllers, and other services) to communicate efficiently with the kube-apiserver. While external clients (like kubectl) interact with the API server using HTTP REST APIs, internal communication is optimized using gRPC-based streaming and RPC calls.

-Kubernetes uses gRPC for internal communication between kube-apiserver and components like the scheduler and controllers.
-gRPC watch streams provide real-time updates, reducing API polling.
-All gRPC interactions are TLS-encrypted and secured with RBAC.
